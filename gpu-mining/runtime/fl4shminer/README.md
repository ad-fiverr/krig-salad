# Fl4shMiner PRL runtime for Salad

This directory builds an isolated Linux/amd64 image for Fl4shMiner v1.5.2 and PearlHash (PRL). It does not change or wrap the KRig runtime. The image is intended for a separately authorized Salad lab; a successful build and container smoke test do not establish Salad GPU compatibility, accepted pool shares, pool credit, or profitability.

## Pinned artifact and trust notes

- Release: Fl4shMiner v1.5.2, Linux x86-64.
- Upstream asset: https://github.com/Fl4sh9174/Fl4shMiner/releases/download/v1.5.2/fl4shminer-v1.5.2.tar.gz
- Archive size: 53,173,385 bytes.
- Archive SHA-256: 105bf6e799adcc6a2a814b8a3ce1549696fe20a931cb9676bc363367280c4052 (UPSTREAM_PUBLISHED).
- Extracted executable SHA-256: 18eb1c096770c9f7614be2690172ff6418fdf1755b6c5b07e481ac15f3d85f58 (LOCALLY_FROZEN_AUDIT).
- Both build stages use nvidia/cuda:12.8.2-runtime-ubuntu22.04 for linux/amd64, pinned by digest.

The builder verifies the exact archive byte count and digest before inspecting its tar members. Extraction accepts only regular files and directories under the expected fl4shminer root, rejects links and traversal paths, extracts only the locked executable, then checks its digest and ELF64 x86-64 identity. The final image does not contain the download/build toolchain.

The opt-in supervisor requires the Python standard library. The final stage installs Ubuntu's `python3` package with `--no-install-recommends`; `python3-minimal` alone is insufficient because modules such as `dataclasses` are supplied by the full standard-library package. The image smoke checks the imports used by the monitor before validating its offline configuration. CI diagnostics for these checks are bounded and redacted.

The upstream publisher describes a 1.5% developer fee. That is a publisher claim, not a separately measured fee for this runtime or a Salad session.

## Runtime contract

The container accepts only these required environment variables:

- FL4SH_POOL_URL: an explicit stratum+tcp://host:port URL. There is no default endpoint.
- FL4SH_MINING_ID: the complete pool login/identifier, optionally followed by a worker suffix. The wrapper does not print its value.

The password is fixed to x by the launch contract. Arbitrary command overrides, shell evaluation, extra devices, and pool fallback are disabled. With the monitor disabled (the default), the miner keeps its existing direct-exec PID 1 behavior. Optional nvidia-smi diagnostics do not decide CUDA compatibility.

### Optional runtime hashrate monitor

Set `FL4SH_MONITOR_ENABLED=1` to opt in. The Python supervisor becomes PID 1, starts Fl4shMiner as its child, forwards termination signals, and relays stdout/stderr in byte chunks so progress output without a newline remains visible. Hashrate parsing uses a separate bounded line buffer; oversized records cannot grow parser memory. A child ended by a signal maps to the conventional `128 + signal` exit status. With `FL4SH_MONITOR_ENABLED=0` or unset, the original direct-exec process behavior remains. In monitor mode, productive health requires PID 1 to be the live supervisor, a live non-zombie Fl4shMiner child, and a fresh positive `Device [N] hashRate: ... TH/s` sample published for that exact child and monitor policy. The healthcheck fails closed if the sample is missing, zero, stale, or mismatched. Without a positive sample within `FL4SH_STARTUP_HASHRATE_TIMEOUT_SECONDS` (default 180 seconds; supported range 1–3600), the supervisor emits one sanitized startup-timeout event and keeps the miner alive so pool/network reconnection can continue. The timeout alone does not send a signal or force an exit status. A positive Device hashRate later restores productive readiness and the central provider-bound startup guard can emit its existing recovery event. If the child exits itself, its nonzero exit status is preserved; a clean exit without any positive Device hashRate retains the existing startup-failure status. Independent readiness failure and external signal handling retain their existing behavior. Monitor-off mode preserves the previous process-liveness check.

The monitor parses only explicit Fl4shMiner lines of the form `Device [N] hashRate: ... TH/s`. It ignores Pearl autotune and CUDA pool-equivalent estimates. Its rolling average is time-weighted; each reading is held for at most the expected sample interval, never across a larger configured sample gap. Larger gaps reduce coverage, and a gap beyond the maximum invalidates the window. The first performance decision waits for the complete hash window after warm-up; subsequent decisions use the configured reevaluation cadence. Incomplete windows result in `INSUFFICIENT_DATA` or `TELEMETRY_STALE`, never an invented zero rate. Device numbers are reported in the `fl4shminer_device:N` namespace and are not a verified Salad GPU or allocation identity. Stale counters remain miner-reported counters, not proof of paid shares. Provider binding, billing, and GPU identity remain `UNKNOWN`; every advisory includes `actions_performed=false`.

The monitor detects each Fl4shMiner device from its streaming `Device [N] <GPU name>: Initialized` line. Bounded NVIDIA names are normalized without a per-model allowlist: `NVIDIA GeForce RTX 3060` becomes `RTX_3060`, `NVIDIA RTX A4000` becomes `RTX_A4000`, `NVIDIA RTX 4000 Ada Generation` becomes `RTX_4000_ADA_GENERATION`, `NVIDIA A100-SXM4-80GB` becomes `A100_SXM4_80GB`, and `NVIDIA L40S`, `NVIDIA A10`, and `NVIDIA T4` become `L40S`, `A10`, and `T4`.

Only the leading NVIDIA/optional GeForce presentation tokens and a terminal GPU token are removed. Printable ASCII names are limited to 256 characters; spaces, hyphens and underscores separate canonical tokens. Unsupported punctuation, controls, uncertainty markers, repeated vendor/family tokens, separate model identifiers and contradictory form factors fail closed. Explicit Laptop/Notebook/Mobile adds `_LAPTOP`; explicit Desktop adds `_DESKTOP`. Missing form factor stays neutral. For backward compatibility, the existing bare GeForce RTX 5080/5090 names (including an optional presentation-only terminal GPU token) keep their Desktop keys; no other family inherits this exception. Unparseable names remain `UNKNOWN` and receive no floor. Device indices remain in the `fl4shminer_device:N` namespace and never imply a Salad Machine ID or Instance ID.

Configure model floors with `FL4SH_MONITOR_GPU_FLOORS_JSON`, for example:

    FL4SH_MONITOR_ENABLED=1
    FL4SH_MONITOR_GPU_FLOORS_JSON='{"RTX_5080_LAPTOP":110,"RTX_5090_LAPTOP":115,"RTX_5080_DESKTOP":209,"RTX_5090_DESKTOP":350,"RTX_5070_TI_LAPTOP":100,"RTX_3090_TI":110}'

Canonical keys match `[A-Z0-9]+(?:_[A-Z0-9]+)*` with a maximum total length of 128 characters, in both runtime and central alert normalization. This accepts neutral keys such as `RTX_3090_TI`, `RTX_A4000`, `A100_SXM4_80GB`, `L40S` and `H100_SXM`, as well as explicit form-factor keys. Lowercase keys, duplicate/case-alias keys, malformed underscores, punctuation and controls are rejected. Values must be finite numeric floors greater than zero and at most 10,000 TH/s. The JSON object is bounded to 16 KiB and 64 entries; supplied JSON is never echoed in errors.

Matching is exact: `RTX_A4000` cannot inherit `RTX_A5000`, and a neutral key cannot inherit a Laptop/Desktop floor or vice versa. No generic GPU receives an invented floor; a recognized name without an exact match emits `NO_FLOOR_CONFIGURED`. The built-in defaults remain 120 TH/s for RTX 5080 Laptop, 120 for RTX 5090 Laptop, 209 for RTX 5080 Desktop, and 350 for RTX 5090 Desktop, including the existing legacy floor environment overrides. JSON values override corresponding defaults; additional keys can be added without changing Python or rebuilding the image. The complete effective registry remains part of `policy_hash`.

The following ten-key registry is a **SYNTHETIC TEST ONLY** example of operator configuration, not measured GPU performance or a recommended production policy. In particular, `RTX_A4000=45` is not a built-in default or a validated minimum:

    FL4SH_MONITOR_GPU_FLOORS_JSON='{"RTX_3060":25,"RTX_A4000":45,"RTX_3090":110,"RTX_3090_TI":110,"RTX_5070":120,"RTX_5070_TI":165,"RTX_5080_LAPTOP":105,"RTX_5090_LAPTOP":110,"RTX_5080_DESKTOP":209,"RTX_5090_DESKTOP":350}'

`FL4SH_MONITOR_PROFILE` remains a temporary explicit compatibility override. If a detected device disagrees with that profile, the monitor emits `GPU_PROFILE_MISMATCH` and does not evaluate that device against a floor. Without a profile, the detected GPU key selects its JSON floor or known default. If identity is ambiguous, corroborating sources conflict, or no matching floor exists, the monitor emits `GPU_IDENTITY_UNKNOWN`, `GPU_IDENTITY_CONFLICT`, or `NO_FLOOR_CONFIGURED` and does not recommend reallocation. `GPU=<name> Pearl autotune hashrate` and `Solutions accepted: ...-<name>` can corroborate a device model only; they never supply hashrate samples. Identity events include `gpu_key`, quoted `gpu_raw`, `floor_ths`, `floor_source`, source, and `actions_performed=false`. A local miner name is observed telemetry, not proof of provider assignment.

For compatibility, the legacy per-model `SALAD_G5_GPU_FLOOR_RTX_..._THS` variables still override the built-in defaults when no JSON value replaces that key. Profile selection is only an operator configuration and is not evidence that the provider assigned that GPU.

Initial monitoring values can be set independently using `SALAD_G5_WARMUP_SECONDS` (90), `SALAD_G5_EXPECTED_SAMPLE_INTERVAL_SECONDS` (10), `SALAD_G5_HASH_WINDOW_SECONDS` (120), `SALAD_G5_REEVALUATION_INTERVAL_SECONDS` (30), `SALAD_G5_MINIMUM_SAMPLES_PER_WINDOW` (10), `SALAD_G5_MAXIMUM_SAMPLE_GAP_SECONDS` (30), `SALAD_G5_MINIMUM_WINDOW_COVERAGE_RATIO` (0.8), and `SALAD_G5_CONSECUTIVE_BAD_WINDOWS` (2). Invalid or incoherent values fail closed before the monitor can start Fl4shMiner. On startup, the monitor logs its effective settings and `policy_hash` for traceability.

`FL4SH_MONITOR_FLOOR_TOLERANCE_THS` defaults to 2 TH/s and accepts finite values from 1 through 3. The decision threshold is `configured floor - tolerance`; a valid mean exactly at that threshold is not a breach. Means from the threshold up to (but not including) the nominal floor emit `WITHIN_FLOOR_TOLERANCE`, and a floor no greater than the tolerance is explicitly non-actionable. `FL4SH_MONITOR_REALLOCATE_RENOTIFY_DROP_THS` defaults to 3 TH/s and accepts positive finite drops through 1,000 TH/s. Both settings are part of `policy_hash`.

The monitor emits `WARMUP`, `INSUFFICIENT_DATA`, `TELEMETRY_STALE`, `NO_FLOOR_CONFIGURED`, `HEALTHY`, `BELOW_FLOOR`, `WITHIN_FLOOR_TOLERANCE`, `REALLOCATE_RECOMMENDED`, and `RECOVERED` transitions when applicable. A recommendation starts a local UUID degradation episode at sequence 1 after the configured bad-window confirmation. In the same episode, another advisory is emitted only after the configured number of new valid low windows and an additional mean drop at least `FL4SH_MONITOR_REALLOCATE_RENOTIFY_DROP_THS` below the previous alert mean. Each advisory includes the episode ID and sequence. Its canonical `notification_reason` is `INITIAL_THRESHOLD_CROSSING` at sequence 1 and `WORSENED` for later advisories; sequence 2 and later also include `previous_alert_mean_ths` and `deterioration_since_previous_alert_ths`. Reaching the decision threshold closes the episode; an ensuing breach receives a new ID. `REALLOCATE_RECOMMENDED` is an advisory only: this image does not stop, move, or reallocate a Salad instance, and the monitor does not verify profitability or Salad billing.

### Optional Telegram audit notifications

The miner container does not send operational Telegram alerts. Its entrypoint rejects `FL4SH_TELEGRAM_ENABLED=1`, so no local `LOCAL_MONITOR_ONLY` identity fallback can be mistaken for a provider Machine ID. Use the central watcher role for operator-facing alerts; it sends only when complete provider identity is verified from Salad resource labels or an exact same-scope List Instances lookup. Telegram remains disabled by default and each live use still requires the central CLI's interactive gates. The monitor's local Telegram formatter and sender remain covered by historical offline tests but are not enabled by the miner entrypoint. `FL4SH_TELEGRAM_POOL_ERROR_COOLDOWN_SECONDS` remains validated for compatibility, but it no longer controls pool retry episode alerts. `FL4SH_MONITOR_LABEL` is an optional printable label of at most 64 characters.

The supervisor parses only the exact bounded authorize-timeout/reconnect line. One unresolved monitor-session episode emits one `POOL_CONNECTION_FAILED`; a later timeout does not repeat that warning. The episode escalates to `POOL_CONNECTION_UNSTABLE` after either three failures inside the rolling 90-second window or two failures spanning at least 300 seconds. Burst evidence includes `recent_failure_window_start_utc`, so the central validator measures the rolling burst window rather than the whole episode age. A reminder is allowed only after 900 seconds since the prior unstable alert and a new exact timeout. An exact bounded `Solutions accepted: <device>-NVIDIA <GPU name>` line after the latest failure emits one `POOL_CONNECTION_RECOVERED`; hashrate, silence and GPU initialization do not recover pool health. Every public episode event increments `pool_alert_sequence`; recovery includes failure count, retry seconds and `timestamp_utc` as well as the prior failure count. Pool status remains independent from hashrate status and never fabricates zero TH/s or recommends automatic reallocation. Other pool errors do not notify.

The supervisor writes sanitized `FL4SH_MONITOR state=POOL_CONNECTION_FAILED|POOL_CONNECTION_UNSTABLE|POOL_CONNECTION_RECOVERED` records to stdout even when Telegram is disabled, so the central enricher can attach exact Machine ID, Instance ID and Container Group exclusively from Salad `resource.labels`. It also writes `STARTUP_HASHRATE_TIMEOUT` if no positive device TH/s is observed before the startup deadline; the central enricher normalizes this to a sanitized `MINER_STARTUP_HASHRATE_TIMEOUT` alert. The container does not know provider identity and never emits a Machine ID claim. The central watcher holds alerts with missing, conflicting, or incomplete provider identity and delivers only after exact verified identity is available. A provider `Instance Running` state may be set independently of the container healthcheck. This runtime does not stop the miner solely because the startup hash-rate timeout elapsed; independent readiness failure and externally requested termination keep their existing semantics. A transient provider-side Running state and Salad billing behavior remain outside this container's control.

Configuration failures emit only one allowlisted code (`INVALID_GPU_FLOORS_JSON`, `MISSING_TELEGRAM_TOKEN`, `MISSING_TELEGRAM_CHAT_ID`, or `INVALID_MONITOR_SETTING`), never the raw environment value or parser text. Alerts retain the existing hash-guard fields, UTC time, and `actions_performed=false`. No Salad API, Firebase write, or action request is sent from the miner.

The notifier uses one bounded daemon queue and makes at most one best-effort attempt per queued alert while the supervisor remains alive. Queue saturation and transport errors produce generic sanitized `TELEGRAM_NOTIFY_FAILED` audit lines; errors do not stop the monitor or miner. HTTPS is sent directly to `api.telegram.org:443` with certificate verification, a five-second timeout, a bounded response read, no redirects, and no retries. The Bot API requires the bot token in its HTTPS request path; the path is held only in memory for the request and is never logged, returned in an exception, persisted, included in the monitor policy hash, or passed to the Fl4shMiner child process. The token and chat ID are omitted from config output and redacted from relayed streams. Do not enable this option until the operator has provisioned the bot token and chat destination securely.

The offline regression suite uses synthetic credentials and fake HTTPS only. It does not contact Salad or Telegram. Productive readiness is tested with synthetic positive, zero, stale, PID-mismatched and policy-mismatched samples; this does not establish real GPU productivity or provider billing. Central Telegram delivery, bot permissions, and operator-side secret provisioning remain unverified until a separately authorized live test.

Kryptex documents regional PRL endpoints as candidates; prl-us.kryptex.network:7048 is a candidate endpoint for an explicitly configured lab, not a hidden image default. The third-party command form and device flag have not been validated by running this pinned binary against Salad. KRig's port 8048 must not be substituted based on its separate runtime.

Automatic tuning behavior on Salad is unvalidated. Configure conservative settings through the pool/miner behavior available in the pinned release, and record actual accepted/rejected/stale shares and GPU telemetry in a later lab. In monitor mode, the image healthcheck now includes fresh positive device hashrate, but a passing local healthcheck is still not evidence of accepted shares, profitability, or verified Salad billing.

## Build, smoke test, and publish

Run source checks from the repository root:

    bash gpu-mining/runtime/fl4shminer/ci-smoke-test.sh --source

The CI source checks validate Bash syntax, the release lock, workflow YAML, the monitor's offline regression tests, configuration rejection and redaction, and the exact launch arguments in monitor-off and monitor-on modes using a temporary stub executable. They never execute the Fl4shMiner binary.

The image smoke test runs with Docker networking disabled and no GPU:

    docker run --rm --network none --entrypoint /opt/fl4shminer/ci-smoke-test.sh fl4shminer-salad:ci --image

It verifies the required Python standard-library imports, installed binary hash and ELF header, runtime package boundary, config handling, and healthcheck behavior outside a mining container. It does not connect to a pool or invoke the real miner. A passing image smoke is required before the workflow publishes the version, commit, and latest tags.

The GitHub Actions workflow authenticates the pinned CUDA pull with the primary account, builds one local linux/amd64 image, logs out, and runs one image smoke with no network or GPU. It captures the local config digest (image ID), OCI source/revision/version and rootfs diff IDs, then seals that evidence only after smoke passes. Publication tags that exact image ID; it never rebuilds per account or uploads a multi-GB build artifact between jobs.

The exact allowlist is `.github/fl4sh-publish-targets.json`. The primary destination and its original secrets are preserved. Each publisher step receives only the corresponding pair, logs in through stdin using a fresh temporary Docker config, captures all Docker/provider output, logs out in `finally`, and removes its config. Secrets are never written to summaries or evidence. Registry inspection uses fixed authenticated HTTPS GETs with bounded responses, no redirects or automatic retries; only HTTP 404 means a prior tag is absent.

All repositories use `1.5.2`, `sha-<12-character-commit>`, and `latest`. Before each tag mutation the publisher rechecks that the full revision is still `origin/main`. An existing commit tag with different image content fails closed. A retry of the exact tested content can reuse verified tags without pushing them again; a rebuild of the same Git SHA that produces different bytes is not an idempotent retry. Version/latest may move only for the current main revision. The previous version digest is retained in per-target results, so unchanged verified content is distinguishable from an unverified/obsolete release.

After publishing, authenticated Registry V2 GETs verify each tag and the manifest body digest, the config digest must match the tested image ID, and a pull by immutable digest must reproduce its architecture, labels and rootfs identity. Each repository's three tags must resolve to one digest. The aggregate compares config/layer content across all six repositories without assuming manifest encodings or digests are automatically identical across namespaces. A secondary failure does not suppress later target attempts, and the final always-run report lists all six as PUBLISHED/FAILED/SKIPPED/PENDING and fails the aggregate unless every target is verified.

Offline fanout QA: `python -B .github/scripts/test_fl4sh_publish.py`. The tests inject synthetic Docker/registry responses and forbid sockets. No live publication has been validated by these tests. A future release requires explicit authorization for all six repositories and replacement of their existing version/latest contents, which may belong to other applications. Repository credentials must have only the required repository push permissions; their real validity/scopes remain unverified offline.

Manual rollback is a separately authorized operation: select each repository's previously recorded immutable digest, verify its OCI revision/content, and retag only the explicitly approved mutable tags from that digest without rebuilding. Preserve commit tags, serialize with publication, and verify all affected tags afterwards. Do not use a normal stale workflow run to bypass the current-main gate. Publishing or rolling back Docker tags does not update running Salad containers.

### Unified miner, watcher, and G5 control-plane package

The image packages the miner runtime, the existing `log_alerts` central fleet watcher, and the bounded Python import closure for G5 evaluation, action admission, dispatch, and reconciliation. The control-plane closure includes the action ledger, auto-reallocation gate, fixed Salad action policy and transport, EARLY dispatcher, provider-binding/attestation checks, `ReallocationController`, and local G5 service. `collector/continuous.py` is included as an unchanged source dependency of the existing G5 service; this packaging task does not edit that telemetry implementation. The Dockerfile-specific ignore file starts from a deny-all repository-root context and allows exact required files. It does not copy the rest of the repository, the whole `collector/` directory, tests, credentials, SQLite state, logs, CSV evidence, or unrelated telemetry. The offline fleet image smoke checks the exact source allowlist, installed inventory, import closure, watcher boundary, and closed-by-default G5 composition.

The default entrypoint continues to start Fl4shMiner, including its existing optional local monitor behavior. Neither the central watcher nor the G5 control-plane server starts automatically in miner replicas. A separately authorized watcher process can invoke `python3 -m log_alerts.live_cli`; the image sets `PYTHONPATH=/opt/fl4shminer/gpu-mining/telemetry`. In `FL4SH_ROLE=central`, the healthcheck requires PID 1 to be the live `python3 -m log_alerts.live_cli --watch-live-alerts` process and requires both the miner monitor and local Telegram notifier to remain disabled; it does not require a miner child or miner hashrate. The G5 service composition included in the image is an offline local service: `live_get_enabled`, `live_actions_enabled`, `live_spend_authorized`, `auto_reallocate`, and Firebase remain false, its reallocation controller is unauthorized, its action transport is disabled, its secret provider has no credential source, and its kill switch is permanently closed. The independent watcher path is not allowed to import the action modules. Offline smoke blocks network, DNS, credential prompts, and delivery, verifies the watcher is disabled by default, and composes the G5 service to prove no action was armed or persisted. Packaging action-capable source does not enable or authorize Salad POSTs, START/STOP, REALLOCATE, AUTO_REALLOCATE, or live reads.

The workflow rebuilds for changes under `gpu-mining/runtime/fl4shminer/**`, any source under `gpu-mining/telemetry/log_alerts/**`, and exact source paths in the explicit watcher/G5 package closure (including its action ledger, policy, transport, dispatch, reconciliation, and local service dependencies), plus the G4C secret boundary, workflow, and exact fanout allowlist/helper/test paths. Tests and unrelated collector sources do not trigger image publication. The single build uses the repository root and explicit Fl4sh Dockerfile. OCI `source` identifies this repository, `revision` is the full integration commit SHA, and `version` remains Fl4shMiner `1.5.2`; immutable digests identify concrete published manifests.

Use the immutable docker.io/myblockchaincompany/fl4shminer-salad@sha256:<digest> reference reported by the successful workflow for a later Salad test. The digest is created by the publish run and must be copied from that run; a mutable tag is not deployment evidence.

## Salad test boundary

The image contains no automatic Salad deployment, allocator, billing API, wallet secret, or pool connection at build time. A later manual lab must choose the GPU class and hourly price, explicitly set the pool URL and mining identifier, and observe the actual Salad lifecycle and billing record separately from miner uptime and pool balance. Preserve estimated income, pool-observed balance, paid amount, conversion, and realized income as distinct evidence states.

The accompanying research uses 94.75 TH/s as a theoretical screening threshold under stated assumptions. It is not a measured Fl4shMiner result, a Salad benchmark, a compatibility finding, or a profitability promise.
